# grpc-task-queue

[![CI](https://github.com/nikolaykonkin/grpc-task-queue/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/nikolaykonkin/grpc-task-queue/actions/workflows/ci.yml)

Учебный pet-проект: очередь задач на gRPC. Два отдельных бинарника общаются по сети через protobuf-контракт:

- **task-api** - gRPC-сервер. Принимает задачи, хранит их в памяти, отдает статус и результат.
- **task-worker** - gRPC-клиент. В цикле забирает задачи у task-api, выполняет их (имитация работы) и отправляет результат обратно.

Проект показывает на простом примере: контракт в protobuf, кодогенерацию, gRPC-сервер и клиент, тесты без сети (bufconn), корректную остановку процессов и CI.

## Схема

```
grpcurl (клиент) ---> task-api <--- task-worker
```

Стрелки показывают, кто к кому обращается: и grpcurl, и воркер являются клиентами task-api. Воркер сам опрашивает сервер, сервер воркеру ничего не отправляет.

Жизненный цикл задачи (разрешены только эти переходы):

```
PENDING --> RUNNING --> DONE
   |           |
   |           +-----> FAILED
   |
   +-----> CANCELLED
```

- Go 1.26

## Быстрый старт

### Что нужно установить

- Go 1.26 или новее
- `make`
- `protoc` и плагины (нужны только если вы меняете `.proto`, готовый сгенерированный код уже лежит в `gen/`)
- `grpcurl` для ручных вызовов

На macOS:

```bash
brew install protobuf grpcurl
go install google.golang.org/protobuf/cmd/protoc-gen-go@latest
go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@latest
```

Папка `$(go env GOPATH)/bin` должна быть в `PATH`, иначе `protoc` не найдет плагины.

### Запуск

```bash
git clone https://github.com/nikolaykonkin/grpc-task-queue.git
cd grpc-task-queue
```

В первом терминале запустите сервер:

```bash
make run-api
```

Во втором терминале запустите воркер:

```bash
make run-worker
```

Третий терминал нужен для вызовов (см. ниже). Адрес по умолчанию `localhost:50051`, его можно поменять флагом: `go run ./cmd/task-api -addr localhost:9000` (то же для воркера).

Если вы изменили `proto/task/v1/task.proto`, перегенерируйте код: `make proto`.

## Примеры вызовов (grpcurl)

Запускайте команды из корня проекта: `grpcurl` читает контракт из папки `proto`. Флаг `-plaintext` означает работу без TLS.

Создать задачу:

```bash
grpcurl -plaintext -import-path proto -proto task/v1/task.proto \
  -d '{"kind":"email","payload":"hello"}' \
  localhost:50051 task.v1.TaskService/SubmitJob
```

Ответ (id и время будут другими):

```json
{
  "job": {
    "id": "3f9c1a7e5b2d4c8aa1e60b7d9c4f2e18",
    "kind": "email",
    "payload": "hello",
    "status": "JOB_STATUS_PENDING",
    "createdAt": "1760000000",
    "updatedAt": "1760000000"
  }
}
```

Время задается в секундах Unix, а 64-битные числа в JSON передаются строками. Это правила преобразования protobuf в JSON.

Получить задачу по id:

```bash
grpcurl -plaintext -import-path proto -proto task/v1/task.proto \
  -d '{"id":"<ID>"}' \
  localhost:50051 task.v1.TaskService/GetJob
```

Список задач (фильтр по статусу, пагинация):

```bash
grpcurl -plaintext -import-path proto -proto task/v1/task.proto \
  -d '{"status":"JOB_STATUS_DONE","limit":10,"offset":0}' \
  localhost:50051 task.v1.TaskService/ListJobs
```

Отменить задачу (пока она PENDING):

```bash
grpcurl -plaintext -import-path proto -proto task/v1/task.proto \
  -d '{"id":"<ID>"}' \
  localhost:50051 task.v1.TaskService/CancelJob
```

Метод `UpdateJobStatus` предназначен для воркера, но его тоже можно вызвать вручную.

Задача с `payload` равным `fail` завершится со статусом `FAILED`: так в учебном воркере проверяется путь с ошибкой.

Пример ошибки (пустой `kind`):

```
ERROR:
  Code: InvalidArgument
  Message: kind is required
```

## Как тестировать

```bash
make test        # обычные тесты
make test-race   # тесты с детектором гонок данных
make vet         # статический анализ (go vet)
```

Что покрыто тестами:

- `internal/storage`: табличные тесты хранилища, переходы статусов, пагинация, конкурентный доступ (много горутин, в том числе гонка нескольких воркеров за одну задачу).
- `internal/server`: тесты всех методов настоящим gRPC-клиентом через bufconn: валидация, коды ошибок, пагинация, гонка воркеров.

## Как это устроено

### Контракт (proto)

Файл `proto/task/v1/task.proto` описывает сервис `TaskService` с пятью unary-методами (`SubmitJob`, `GetJob`, `ListJobs`, `CancelJob`, `UpdateJobStatus`), сообщение `Job` и enum `JobStatus`. Для каждого метода есть отдельная пара запрос-ответ, чтобы методы развивались независимо. Нулевое значение enum `JOB_STATUS_UNSPECIFIED` в `ListJobs` означает «без фильтра». Версия `v1` в пути нужна, чтобы в будущем можно было выпустить несовместимый `v2`.

### Кодогенерация

`make proto` запускает `protoc` с двумя плагинами. `protoc-gen-go` создает `task.pb.go` (структуры и сериализация), а `protoc-gen-go-grpc` создает `task_grpc.pb.go` (интерфейсы клиента и сервера). Сгенерированный код хранится в репозитории, чтобы проект собирался обычным `go build` без установленного `protoc`.

### Хранилище

`internal/storage` хранит задачи в `map[string]*Job` под `sync.RWMutex` (чтение не блокирует другие чтения). Порядок создания хранится отдельно, поэтому очередь честная (первой берется самая старая задача), а страницы в `ListJobs` стабильны. Методы возвращают копии задач, чтобы снаружи нельзя было изменить данные в обход блокировки. Правила переходов между статусами проверяются внутри хранилища под той же блокировкой, что и запись: поэтому два воркера не смогут взять одну задачу. id генерируется из 16 случайных байт `crypto/rand` в виде hex-строки.

### Сервер

`internal/server` реализует интерфейс `TaskServiceServer`. Он проверяет вход (`kind` не длиннее 50 символов, `payload` не длиннее 10000, длина считается в символах, а не в байтах), переводит типы хранилища в protobuf-типы и ошибки хранилища в коды статуса gRPC. В `ListJobs` по умолчанию возвращается 50 задач, максимум 100.

### Воркер

`cmd/task-worker` раз в секунду просит у сервера самую старую задачу в статусе PENDING, пытается перевести ее в RUNNING, «выполняет» (спит 2 секунды) и отправляет `DONE` или `FAILED`. Если задачу успел занять другой воркер, сервер вернет `FailedPrecondition`, и воркер просто пропустит ее. Воркер вынесен в отдельный процесс: его можно перезапускать и запускать несколько штук независимо от сервера. Результат отправляется отдельным контекстом, чтобы остановка по Ctrl+C не оставила задачу в статусе RUNNING.

### Остановка процессов

Оба бинарника обрабатывают `SIGINT` и `SIGTERM`. Сервер вызывает `GracefulStop` (дожидается текущих запросов) с таймаутом 10 секунд, после чего останавливается принудительно. Воркер доделывает текущую задачу и выходит.

### Обработка ошибок (коды статуса gRPC)

| Код | Когда возвращается |
|---|---|
| `InvalidArgument` | пустой id, пустые или слишком длинные `kind` и `payload`, отрицательные `limit` и `offset`, недопустимый статус |
| `NotFound` | задачи с таким id нет |
| `FailedPrecondition` | запрос корректен, но статус задачи не позволяет операцию (например, отменить задачу в RUNNING) |
| `Internal` | непредвиденная ошибка сервера (подробности только в логе, клиенту общий текст) |

## Что не реализовано и почему

Проект учебный, и это осознанные упрощения:

- **Потоковая передача (streaming).** Все методы унарные (unary): один запрос, один ответ. Для демонстрации основ gRPC этого достаточно. Серверный streaming позволил бы отправлять задачи воркеру без опроса, но заметно усложнил бы код.
- **Персистентность (постоянное хранение данных).** Задачи хранятся в памяти: при перезапуске task-api все теряется, а несколько экземпляров сервера не будут видеть задачи друг друга. Для настоящей системы нужна база данных (например, PostgreSQL).
- **Повторные попытки (retry) и нарастающие паузы (backoff).** Если сервер недоступен, воркер пишет ошибку в лог и повторяет попытку на следующей итерации цикла. Но продуманной стратегии повторов нет: не ограничено число попыток и нет пауз, которые растут с каждой неудачей, чтобы не перегружать недоступный сервер.
- **Защита от зависших задач.** Если воркер упадет во время работы, задача навсегда останется в статусе RUNNING. В настоящих системах для этого используют аренду задачи с истечением срока или проверку «воркер жив».
- **Безопасность.** Нет TLS и аутентификации, поэтому сервер по умолчанию слушает только `localhost`.
- **Метрики, трассировка (tracing) и перехватчики (interceptors).** Метрики и трассировка показывают, как сервис работает в боевой среде. Перехватчики это код, который gRPC автоматически выполняет до и после каждого вызова (аналог middleware в HTTP): через них обычно делают логирование, проверку доступа и сбор метрик. Для демонстрации они не нужны и усложнили бы проект.
- **Пагинация по курсору.** Используются `limit` и `offset`: проще, но при активной записи страницы могут «сдвигаться».
- **Удаление задач.** Завершенные задачи остаются в памяти навсегда.

## CI

Workflow `.github/workflows/ci.yml` запускается при каждом пуше в `main` и при каждом pull request. Он ставит Go той версии, что указана в `go.mod`, и выполняет:

- `go vet ./...` для статического анализа;
- `go test -race ./...` для тестов с детектором гонок данных. Гонки проявляются не при каждом запуске, а в CI проверка выполняется всегда одинаково.

Так проект проверяется на чистой машине, а не только у автора.
